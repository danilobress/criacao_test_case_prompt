# Documentação de Testes de Contrato de API - Serviço de Estoque (Stock-Service)

**Especialidade:** Engenharia de Qualidade de Software / SDET Sênior  
**Tipo de Teste:** Testes de Contrato de API (Validação de Esquemas JSON, Envelopes HTTP e Protocolos)  
**Serviço / Provedor:** Serviço Interno de Gestão de Estoque e Produtos (`Stock-Service`)  
**Endpoint:** `POST /v1/estoque/reservar`  
**Especificação Formal:** [stock-api-openapi.yaml](../stock-api-openapi.yaml)

---

## Escopo e Diretrizes de Testes de Contrato

- **Objetivo Estrito:** Validar exclusivamente a "forma do envelope" (tipagem, formatos primitivos, conformidade de schemas JSON Schema, headers HTTP e códigos de status).
- **Isolamento de Negócio:** Ignoram-se regras de saldo físico de armazém, cálculos ou estados transacionais do banco de dados. Os testes avaliam a integridade do contrato sintático entre consumidor e provedor.

| **CT-Contrato-024 - Validação Estrutural do Envelope de Falha de Reserva (422 Unprocessable Entity)** | Validar a conformidade contratual do schema estendido `FalhaReservaProblemDetails` e sua sub-estrutura `itensIndisponiveis`. | - Status HTTP `422 Unprocessable Entity`.<br>- Header `Content-Type: application/problem+json`.<br>- Envelope contendo campos base (`type`, `title`, `status = 422`, `detail`, `instance`).<br>- Atributo `itensIndisponiveis` é um array onde cada elemento obedece à tipagem estrita:<br>  * `produtoId`: string.<br>  * `solicitado`: integer.<br>  * `disponivel`: integer. | - Provedor de Estoque ou Mock Prism com `Prefer: code=422`. | **Passo 1 (Disparar Resposta 422)**<br>• **Ação:** Enviar requisição `POST /v1/estoque/reservar` com [`payloads/estoque-reserva-saldo-insuficiente.json`](../payloads/estoque-reserva-saldo-insuficiente.json).<br>• **Dados de Entrada:** Headers: `Content-Type: application/json`, `Prefer: code=422`.<br>• **Resultado Esperado:** Retorno HTTP `422 Unprocessable Entity`.<br><br>**Passo 2 (Auditar Estrutura e Tipagem de itensIndisponiveis)**<br>• **Ação:** Inspecionar a coleção `itensIndisponiveis` contra o JSON Schema.<br>• **Dados de Entrada:** Body retornado no Passo 1.<br>• **Resultado Esperado:** Tipagem exata em cada campo (`solicitado` e `disponivel` inteiros, `produtoId` string). |
| **CT-Contrato-025 - Validação Estrutural do Envelope de Erro Interno (500 Internal Server Error)** | Validar a integridade estrutural e ausência de desvios de contrato no envelope de erro de banco de dados emitido pelo Estoque. | - Resposta `500` adere estritamente ao schema `ProblemDetails`.<br>- Header `Content-Type: application/problem+json`.<br>- Campo `status: 500`.<br>- Campo `instance: "/v1/estoque/reservar"`. | - Provedor de Estoque ou Mock Prism na porta `4011`. | **Passo 1 (Validar Envelope 500)**<br>• **Ação:** Enviar chamada com `Prefer: code=500`.<br>• **Dados de Entrada:** Headers padrão + `Prefer: code=500`; Body válido.<br>• **Resultado Esperado:** Retorno HTTP `500 Internal Server Error`; body ProblemDetails com `status: 500`.<br><br>**Passo 2 (Auditar Schema)**<br>• **Ação:** Validar tipos e propriedades do body contra `ProblemDetails`.<br>• **Dados de Entrada:** Resposta do Passo 1.<br>• **Resultado Esperado:** Schema válido sem campos não mapeados. |
| **CT-Contrato-026 - Injeção de Campos Não Mapeados no Envelope Raiz de Reserva (Additional Properties)** | Verificar a política contratual do provedor de Estoque diante de campos extras não documentados na raiz do payload `ReservaEstoqueInput`. | - Dependendo da política de extensibilidade da API:<br>  * Rejeição com `400 Bad Request` caso `additionalProperties: false`, OU<br>  * Aceitação com `200 OK` ignorando os campos espúrios, sem refleti-los na resposta. | - Servidor de Estoque operacional. | **Passo 1 (Submeter Payload com Atributo Inexistente)**<br>• **Ação:** Enviar requisição `POST /v1/estoque/reservar` contendo campo não mapeado `"armazemDestino": "SP-01"`.<br>• **Dados de Entrada:** Headers padrão; Payload `R0` com chave extra.<br>• **Resultado Esperado:** A API não quebra com 500; responde com 400 ou 200 (ignorando o campo espúrio).<br><br>**Passo 2 (Verificar Não-Vazamento no Response)**<br>• **Ação:** Em caso de retorno 200, auditar o body de retorno.<br>• **Dados de Entrada:** Resposta do Passo 1.<br>• **Resultado Esperado:** O campo espúrio não é refletido no objeto `ReservaEstoqueResponse`. |
| **CT-Contrato-027 - Injeção de Campos Não Mapeados no Item de Reserva** | Validar que campos exclusivos do catálogo/checkout (como `precoUnitario`) injetados no item da reserva são tratados com segurança conforme o contrato. | - A API não entra em erro inesperado.<br>- Responde com `400 Bad Request` ou ignora os campos que não pertencem ao contrato de estoque. | - Servidor de Estoque operacional. | **Passo 1 (Submeter Item com Campo precoUnitario)**<br>• **Ação:** Enviar `POST /v1/estoque/reservar` com item contendo campo extra `"precoUnitario": 49.90`.<br>• **Dados de Entrada:** Payload contendo propriedade de preço (inexistente no schema de estoque).<br>• **Resultado Esperado:** Resposta conforme a política contratual definida (400 ou 200). |

| **CT-Contrato-030 - Validação de Tipagem Estrita do TTL (tempoExpiracaoSegundos)** | Validar que a propriedade `tempoExpiracaoSegundos` é retornada estritamente como tipo integer positivo, sem decimais ou conversão para string. | - Campo `tempoExpiracaoSegundos` é do tipo `integer`.<br>- Valor estritamente maior que zero (> 0). | - Servidor de Estoque operacional. | **Passo 1 (Submeter Reserva)**<br>• **Ação:** Enviar requisição `POST /v1/estoque/reservar`.<br>• **Dados de Entrada:** Payload `estoque-reserva-sucesso.json`.<br>• **Resultado Esperado:** Retorno HTTP `200 OK`.<br><br>**Passo 2 (Inspecionar Tipagem do Campo)**<br>• **Ação:** Checar o tipo primitivo de `tempoExpiracaoSegundos`.<br>• **Dados de Entrada:** Resposta do Passo 1.<br>• **Resultado Esperado:** Tipo primitivo é `integer`, com valor em conformidade com o schema OpenAPI (ex.: 900). |
| **CT-Contrato-031 - Validação Sintática: JSON Malformado / Truncado** | Validar tratamento de erro de parsing quando o body da requisição não é um JSON válido. | - Status HTTP retornado: `400 Bad Request`.<br>- Resposta indicando falha na formatação JSON. | - Servidor de Estoque ou Mock Prism na porta `4011` operacional. | **Passo 1 (Submeter JSON Corrompido)**<br>• **Ação:** Enviar requisição `POST /v1/estoque/reservar` com string corrompida: `{"pedidoReferenciaId": "temp-ped-9821", "itens": [`.<br>• **Dados de Entrada:** Headers padrão; String inválida.<br>• **Resultado Esperado:** Retorno imediato HTTP `400 Bad Request`. |
